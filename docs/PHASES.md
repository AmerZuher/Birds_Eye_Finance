### Environment notes (not app bugs — device/OS specific, but worth knowing)
- **Expo Go cannot run this app.** It only ships Expo's own SDK modules — no `react-native-mmkv` (v4, Nitro-based), `react-native-nitro-modules`, or `react-native-worklets`. Opening it in Expo Go crashes with a generic "app has a bug" dialog. Always use a dev client (`npx expo run:android` / `run:ios`, or an EAS dev build).
- **WSL2 + a Windows-side Android emulator**: if the dev machine is WSL2 with Android Studio/AVDs installed on the Windows side (not inside WSL), `npx expo run:android` looks for devices via the SDK copy of `adb` at `$ANDROID_HOME/platform-tools/adb` specifically. If that's a native Linux `adb` binary, it spins up its own isolated server inside WSL with zero knowledge of the Windows-hosted emulator — `adb devices` from a plain shell can look fine (if e.g. `/usr/bin/adb` happens to be a symlink to the real Windows `adb.exe`) while Expo's own device detection still fails with "No Android connected device found." Fix: make `$ANDROID_HOME/platform-tools/adb` itself a symlink to the Windows `adb.exe` (typically at `/mnt/c/Users/<user>/AppData/Local/Android/Sdk/platform-tools/adb.exe`) so there's only one real adb server in play. Don't bother with `ADB_SERVER_SOCKET` TCP-bridging — WSL2 runs Windows `.exe` files directly through its own interop layer, no networking needed.

### Metro/Babel/toolchain gotchas discovered this phase (read before touching config files)
This project was scaffolded on Expo SDK 57 (RN 0.86, React 19.2, TS 6.0) — noticeably newer than most existing guides/muscle memory. Things that broke and how they were fixed, so nobody rediscovers these the hard way:
- **`react-native-mmkv` v4** dropped the `new MMKV()` class entirely — it's now Nitro-modules-based. Use `createMMKV({ id })` from `react-native-mmkv`, and you must also install the `react-native-nitro-modules` peer dependency explicitly (`npx expo install react-native-nitro-modules`). See `src/lib/mmkv.ts`.
- **`react-native-reanimated` v4** split its Babel plugin's dependency out into a separate `react-native-worklets` package. If bundling fails with `Cannot find module 'react-native-worklets/plugin'`, run `npx expo install react-native-worklets` (it's an implicit peer dep, easy to lose across `npm install` churn since nothing in package.json otherwise requires it).
- **`expo-router`'s `Tabs`** no longer wraps `@react-navigation/bottom-tabs` as an external dependency — it vendors its own fork (there is no `@react-navigation/*` in `node_modules` at all). Import `Tabs`/`BottomTabBarProps` from `'expo-router/js-tabs'`, not the deprecated default `Tabs` export off `'expo-router'`. The custom tab bar goes on `<Tabs tabBar={...}>` directly — **not** inside `screenOptions` (that will fail to typecheck; `tabBar` lives on the navigator config, `screenOptions` is per-screen).
- **NativeWind v4** installs against **Tailwind v3**, not v4 — `npm install nativewind tailwindcss` without pinning pulls Tailwind v4 by default (a completely different CSS-native config model) and doesn't work right with NativeWind 4.x. Pin `tailwindcss@^3.4.4`.
- **Drizzle + expo-sqlite migrations**: `drizzle-kit generate` (dialect `sqlite`, driver `expo`) emits a `migrations.js` that does `import m0000 from './0000_xxx.sql'`. Two things are required for this to bundle: add `.sql` to `metro.config.js`'s `resolver.sourceExts`, **and** add the `babel-plugin-inline-import` Babel plugin configured for `['.sql']` extensions (otherwise Metro tries to parse the raw SQL as JavaScript and fails with "Missing semicolon").
- **`babel-preset-expo`** wasn't hoisted to top-level `node_modules` after a chain of `--legacy-peer-deps` installs (it ended up nested under `node_modules/expo/node_modules/babel-preset-expo`), which broke Babel's preset resolution from `babel.config.js`. Fixed by adding it as an explicit top-level devDependency. If a fresh `npm install` ever un-hoists it again, that's the symptom to look for.
- **ESLint 10** (installed by default via `eslint-config-expo`'s loose `>=8.10` peer range) is incompatible with the `eslint-plugin-react` version currently bundled — it calls the removed `context.getFilename()` API and crashes the linter entirely. Pinned `eslint@^9` in devDependencies as a workaround; revisit if `eslint-config-expo` bumps its bundled `eslint-plugin-react`.
- **TypeScript 6.0** deprecates the `baseUrl` compiler option (needed for the `@/*` path aliases) — add `"ignoreDeprecations": "6.0"` to silence the error until this project migrates off `baseUrl` before TS 7.
- **`.npmrc`** sets `legacy-peer-deps=true` project-wide — `expo-router`'s web preview pulls in `@radix-ui/*`/`vaul` packages with a peer-dependency graph that conflicts with our React 19.2 pin otherwise.
- The React Compiler–oriented ESLint rules (`react-hooks/set-state-in-effect`, `react-hooks/immutability`, `react-hooks/refs`, all new in this `eslint-config-expo`) flag Reanimated's `.value =` mutation pattern and classic `Animated.Value` ref access as violations even though both are the libraries' documented, correct usage. `GlassModal.tsx` has a targeted file-level disable with a comment; `ToggleSwitch.tsx` was rewritten to use `useSharedValue`/`useAnimatedStyle` instead of classic `Animated`, which sidesteps the ref-access rule entirely — prefer that approach over disabling the rule where practical.
- `app.json`: `newArchEnabled` is no longer a valid top-level key on SDK 57 (New Architecture is the only architecture now) — `expo-doctor` will flag it as an unknown schema property.

Scope and design approved 2026-09-16 (ENHANCEMENT_PLAN §6, decisions 5–8).

- **What it is:** a `balance_snapshots` table (id, date, amount, currency, note?, createdAt) — the user logs "here's what I actually have today", and the app compares it with what it expected.
- **Expected** = last logged balance + netSavings × (days since that log ÷ 30.44). **Variance** = logged − expected.
- **Home** shows the latest logged balance (aged forward) instead of the sum of the typed accounts, which stay in Edit Profile as the seed and the per-account detail; a `ReconciliationNudgeCard` appears when the last log is stale (30 days).
- **Analytics** gains `VarianceHistoryChart` — the expected-vs-actual trend across logged periods.
- **The FAB** on Home and Analytics opens Log Balance directly (ENHANCEMENT_PLAN §5's three-entry sheet waits for targets/investments).
- **Not in scope:** targets, investments, reconciliation-driven forecasting beyond the variance line — rule 13 is untouched.

### Step 0 — `lastReconciledDate` removed (2026-09-16)
Groundwork, done ahead of the reconciliation work and independent of the two pending rule changes. The field was stamped on every balance add/remove and on an import, and **read nowhere**; 2.3.0 derives the last reconciliation from `MAX(date)` on `balance_snapshots`, so keeping a second copy in the MMKV profile would only invite drift (the same reason debt status is derived, never stored). Checked: `npm run check` (0 errors; the 4 known react-hook-form warnings), Prettier on the four changed files. No translation keys and no native change — reloading the dev build is enough.
- `Profile.lastReconciledDate` gone from `src/constants/initialData.ts`; the two writes in `EditProfileScreen.tsx` (`addBalance`, `removeBalance`) and the one in `dataTransfer.ts`'s `profilePatchForImport` are gone with it, each collapsing to a single-line `updateProfile`/assignment.
- `UserContext.readInitialProfile` now drops the key when it reads the stored blob, so an existing install stops rewriting it — and stops re-exporting it, since an export carries the profile wholesale. Old export files that still carry it are ignored: `parseSnapshot` only reads the fields it knows.
- FEATURE_SPEC 0.7 (persistence map and the launch-cleanup line), 3.3 (the balances manager no longer "stamps lastReconciledDate = now") and Part 5's `Profile` interface updated. The mentions left in `docs/BOOTSTRAP_PROMPT.md` and this file's Phase 1–2 blocks are history, deliberately untouched.

### Step 1 — spec, data model and the reconciliation core (2026-09-16)
Written to spec first, then built (the user's order). **Docs (before any code).** FEATURE_SPEC: 0.1 (the FAB on Dashboard/Analytics), 0.7 (the new table and the nudge-dismissal key), 0.8 and the source-file list, Part 5 (the `BalanceSnapshot` row type and the derived reconciliation values), Part 6 (four new quirks — today's net savings ages past intervals, the balance drifts between logs, a same-day log replaces, and removing the last log falls back to the accounts), Part 7 rewritten (7.3 Current balance, 7.4 Balance check, the rest renumbered to 7.8), Part 8 (8.3 Expected vs actual, renumbered to 8.6), and a new **Part 9 — LOG BALANCE**. DEVELOPMENT.md: the structure map, the data-layer list, and the provider tree (which also gained the `UpdatesProvider` it had been missing since 2.2.0). The `7.x` references in `Dashboard.tsx`, `Debts.tsx` and `ChromeContext.tsx` were renumbered with the spec.

- **`balance_snapshots`** (`src/db/schema.ts`, migration `0006_balance_snapshots.sql`): `id, date, amount, currency, note?, createdAt`, indexed by date. Amount and currency are stored as typed and converted at render time, like every other amount. One row per date is a *write-side* rule, deliberately not a unique index — the read side breaks ties on `createdAt` then id, so an imported duplicate can't fail an insert.
- **`src/lib/reconciliation.ts`** (new, pure): `expectedAt`, `snapshotHistory`, `latestSnapshot`, `daysSinceLog`, `isBalanceStale`, `isOnTrack`, `STALE_AFTER_DAYS`. `30.44` is now `DAYS_PER_MONTH` in `src/lib/period.ts`, which `getMonthlyEquivalent` also reads, so the aging and the period math can't drift apart.
- **`src/context/BalanceContext.tsx`** (new, mounted between `FinanceProvider` and `ChromeProvider`): the live query, `logBalance` (updates today's row if there is one), `deleteSnapshot`, and the derived `currentBalance`, `history`, `latestVariance`, `daysSince`, `isStale`.
- **`LogBalanceSheet`** (FEATURE_SPEC Part 9): GlassModal + react-hook-form/zod, AmountInput with a currency pill, an optional note, dated today. Mounted once at the root, opened through `ChromeContext.openLogBalance` — the FAB on Dashboard/Analytics, the hero's link and the nudge all open the same instance. Reopening on a day that already has a log prefills it and says it will be replaced.
- **Dashboard 7.3/7.4:** the hero is now the logged balance aged forward, with a caption naming its age (and, once a day old, the figure as logged), a variance line that opens Analytics, and a "Log balance" link before the first log. `ReconciliationNudgeCard` appears past 30 days; dismissing it snoozes it for 7 days (one MMKV key) rather than silencing it.
- **Analytics 8.3:** `VarianceHistoryChart` — up to 6 intervals, newest first, each a capped ProgressBar of actual ÷ expected colored by the sign of the variance, over one factual line about the latest interval. No category attribution: the app can't know which category caused a gap.
- **Primitives:** `BalanceRevealCard` gained the caption, variance and action slots ENHANCEMENT_PLAN §2 anticipated (the variance masks with the card, so tapping to reveal never changes its height); `ReconciliationNudgeCard` and `VarianceHistoryChart` are new. 27 `logBalance.*`/`dashboard.*`/`analytics.variance.*` keys per language.

**Four open questions, answered 2026-09-16 (all as recommended):**
- **Balance logs travel with an export.** `balanceSnapshots` joins `BackupSnapshot` (`buildSnapshot`, `parseSnapshot`, `appendSnapshot`), with its own count in the import preview, the confirmation and the success banner. A log needs a real date and a numeric amount to be imported; ids are regenerated like every other row; files written before 2.3.0 carry none. Re-importing is harmless: `snapshotHistory` now collapses a date to its last-written row (`oneLogPerDate`), so a duplicated date can't produce a zero-day interval with a meaningless variance — which also covers duplicates from any other source, not just imports.
- **An older log is deleted from the chart row.** Tapping a row in Analytics 8.3 opens the standard delete `ConfirmModal`; today's log is still corrected by logging again. No edit sheet and no history screen — targets and investments will reshape that surface anyway.
- **No backdating** in the sheet: the date stays a read-only "today" line. A date field would let a backdated row silently rewrite the variance of the log after it.
- **The insight line stays factual** ("{amount} less than expected over {n} days"), not the category attribution ENHANCEMENT_PLAN §4 floated: the app has no per-day spending history, so attribution would credit the gap to whichever category happens to be large today — confidently wrong, next to numbers that are honest.

### Step 2 — dates are picked, not typed (2026-09-20)
User's call: every date field was a plain `TextField` with a `YYYY-MM-DD` placeholder — a debt's date, its installment start and end dates, and a ledger entry's date. Checked: `npm run check` (0 errors; the same 5 warnings), Prettier on every changed file, EN/AR keys 430/430 with every literal `t()` key present, and a 17-case logic test of the calendar helpers (month lengths, leap February, the first weekday, the worst-case month that needs all six rows, the locale forms) run with `tsx`. **Not verified on a device.** No native change and no new dependency — reloading the dev build is enough.
- **`DateField`** (`src/components/ui/DateField.tsx`, primitive 29 — CLAUDE.md rule 4 updated, and rule 5 now says dates are picked): the shared field look from `useTextFieldStyle` (not a re-styled copy) with a calendar glyph, opening a month grid in a `GlassModal` — the same nested-sheet pattern `CustomSelect` already uses from inside a form. Previous/next month arrows through `IconButton`'s `directional` RTL flip, weekday headings, a fixed six-row grid so the sheet never changes height, the selected day filled with the accent and today outlined, out-of-range days dimmed and untappable, and "Today" / "Clear" links (Clear only where the date is optional). Picking a day closes the sheet — no confirm step.
- **Built in JS, not on Android's date dialog.** The system dialog follows the OS's day/night theme, which this app deliberately doesn't control (DEVELOPMENT.md gotcha 9), so it would open light over a dark theme with none of the app's material — and it would need a native dependency and a prebuild. This way it is themed, mirrors in Arabic and needs neither.
- **Localization** (`src/lib/dates.ts`): `monthLabel`, `weekdayInitials`, `formatDayNumber` plus the grid helpers `daysInMonth`, `firstWeekdayOfMonth`, `toDateStr`. Day numbers use the same `ar-SA-u-nu-arab` tag `CurrencyContext` formats amounts with, so the calendar's digits match every amount; date names pin `-ca-gregory`, since an ICU build that defaults `ar-SA` to Umm al-Qura would otherwise print a Hijri month over a Gregorian grid. Each helper falls back to ASCII if `Intl` data is missing — a wrong-language header beats a sheet that throws while rendering.
- **Call sites:** `DebtModal` (date, installment start, installment end) and `AdjustmentSheet` (entry date). The end date is `clearable` and takes `min={startDate}`, so a plan can no longer end before it begins — a constraint that falls out of the picker rather than a new validation rule. The zod date rules stay as guards for imported and older records.
- The four "(YYYY-MM-DD)" error strings now read as picker wording in both languages. 5 `dateField.*` keys per language.

**Field restyled, then tightened, the same day** (user: "the calendar looks great, the date field is the problem"). It was the one field still wearing a plain text input's clothes: a raw `2026-09-20` — a stored value, not a written date — in a box lighter than the AMOUNT block above it, with a small tertiary glyph at the far end that reads as decoration rather than a control. It now takes AmountInput's anatomy: label inside the box, a theme-tinted pill (calendar + chevron) as the affordance, "20 September 2026" as the value, the weekday beneath it (the context a bare date never carries — "is the 20th a Sunday?" is what someone checks before agreeing to a payment date), and an accent "Today" Badge when it is today. `formatDateLong`/`formatDateMedium`/`weekdayName` joined `src/lib/dates.ts` with the same locale tags and fallbacks. The installment pair uses a new `compact` variant — short date, no badge — since those two share a row.

Two follow-ups from the user's screenshot (2026-09-20): the weekday line came back out — it pushed the pill and the value off each other's centre line for context that wasn't wanted — so the block is one row again, and `weekdayName` went with it rather than sitting unused. And **NOTES was the last field wearing its label outside its box**, which is what made it read as lighter than the amount and date blocks above it. `FormField.tsx` gained `FieldBox` (label inside, the shape AmountInput and DateField already had), `TextField`'s `bare` look for an input already inside one, and `TextFieldBlock` composing the two; the notes field in DebtModal and the note in AdjustmentSheet use it. The label style itself is now one function both shapes read, so the two can't drift. Person name and monthly payment keep their outside labels for that reason — say if you want those moved too.
